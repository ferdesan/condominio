# ADR-004: Dialog-Based Create and Edit, With a Detail Route Only for Condominiums

## Status

Accepted

## Date

2026-09-12

## Context

The four modules differ sharply in record count and field count. Condominiums have roughly twenty editable fields but few records per tenant, and the backend exposes a statistics endpoint per condominium returning unit totals, occupancy, resident and vehicle counts, open incidents, pending charges and pending reservations. The source specification for condominiums asks for a "details" view showing a complete summary. Units, residents and reservations each have fewer fields and many more records, and their specifications describe only listing, registration and editing.

The design system already provides a dialog primitive and a confirmation dialog, both built and documented. It provides no form wrapper, and no routing convention exists for nested resource views since the application has exactly one real route today.

A síndico onboarding a building registers many units and residents in sequence. Any flow that navigates away from the list discards the active filters, the search term and the page position on every save.

## Decision

Create and edit happen in a dialog over the list in all four modules. Destructive actions use the existing confirmation dialog.

Condominiums additionally gain a detail route at `/condominios/:id` presenting the full record alongside the statistics the backend already computes. The other three modules have no detail route; their dialogs serve both entry and revision.

## Alternatives Considered

### Alternative 1: Dedicated pages for every action

- **Description**: Separate routes for create, edit and detail across all four modules.
- **Pros**: Shareable URLs for every state; more room for the twenty-field condominium form; browser history navigates the flow.
- **Cons**: Twelve additional routes; the list's filter, search and pagination state is lost on every action unless separately preserved; no reuse of the dialog components already built and documented.
- **Why rejected**: The cost falls hardest on exactly the flow that matters most — sequential registration during onboarding.

### Alternative 2: Dialogs everywhere, including a read-only dialog for the condominium summary

- **Description**: All four modules are list plus dialog, with the condominium summary shown in a dialog.
- **Pros**: Maximum consistency; smallest surface.
- **Cons**: Compresses twenty fields plus seven statistics into a constrained dialog; leaves the statistics endpoint underused; a summary worth consulting is not worth a modal that closes on a stray click.
- **Why rejected**: The condominium summary is reference material a síndico returns to, which is what a page is for.

## Consequences

### Positive

- List context — filters, search term, page — survives every create and edit.
- The dialog and confirmation components already built are used as intended rather than duplicated.
- Only one new route joins the router, keeping the navigation model close to what exists.

### Negative

- A specific unit, resident or reservation cannot be linked to directly, since only the list route exists for those modules.
- The condominium form is the largest one in the effort and must fit a dialog, which will require a wider variant than the default.

### Risks

- **Risk**: A dialog form with unsaved changes dismissed by a click outside loses the user's work. **Mitigation**: Dismissal of a dirty form must ask for confirmation rather than closing silently.

## Implementation Notes

Activating a screen requires registering its real route and removing it from the set that routes to the placeholder component; the router generates placeholder routes for every navigation entry not in that set.

Every screen sits inside the authenticated shell, which already provides the selected condominium through a context available to all four modules. Condominium mutations must also refresh the condominium list that feeds the shell's selector, since both read the same collection.
