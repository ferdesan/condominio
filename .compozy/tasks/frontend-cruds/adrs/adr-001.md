# ADR-001: Frontend-Only Scope Over the Existing API Contract

## Status

Accepted

## Date

2026-09-12

## Context

The platform's backend is complete for the four domains in question. All 27 REST modules are registered, and `condominiums`, `units`, `residents`, and `reservations` each expose the seven standard CRUD endpoints plus domain-specific extras, with business rules already enforced server-side (plan limits, document uniqueness, slot validation, automatic unit-status synchronisation). Backend integration tests cover all four domains and act as an executable contract.

The frontend, by contrast, has exactly one real page. Every other navigation entry resolves to a placeholder component, gated by `const IMPLEMENTED = new Set(['/'])`. The product map is visible in the sidebar but nothing behind it works.

Market research surfaced three capabilities that established competitors treat as table stakes: CSV import with column mapping (identified as the single largest onboarding blocker in the sector), grid export for accountability reporting, and reservation waiting lists. None of the three can be satisfied by the current API — each would require new endpoints, new persistence, and in the import case a staging and preview mechanism.

This creates a tension between market completeness and delivery scope.

## Decision

This effort delivers the frontend layer only. Every requirement in the PRD must be satisfiable by an endpoint that exists in the backend today.

Capabilities requiring new server-side surface are excluded and recorded in Non-Goals with their business rationale intact, so a later effort can pick them up without re-deriving the research.

Two boundary clarifications:

1. The frontend type definitions may be extended or corrected where they are incomplete relative to what the API already returns. This is frontend work, not a contract change.
2. Repairing the continuous integration pipeline is in scope. The pipeline currently fails because the frontend test command runs a test runner against zero test files and exits non-zero, which blocks every downstream job. Shipping four modules behind a permanently red pipeline would leave the delivery unverifiable.

## Alternatives Considered

### Alternative 1: Frontend plus backend extensions for import and export

- **Description**: Add CSV import for units and residents, plus grid export, alongside the four screens.
- **Pros**: Addresses the highest-value gap found in market research; import is the documented conversion blocker for competitors; delivers a complete onboarding path.
- **Cons**: Roughly doubles the scope; mixes two layers with different testing and review needs in one workflow; import demands a staging, mapping and preview design that is a product in itself; blocks frontend tasks behind backend tasks.
- **Why rejected**: The stated mandate was the frontend layer, and the backend is the one part of this system that is already finished and tested. Expanding into it trades a deliverable outcome for a partially-finished one across two layers.

### Alternative 2: Minimal scope — screens only, market findings discarded

- **Description**: Build the four CRUDs and record nothing about the excluded capabilities.
- **Pros**: Smallest possible document; no speculative content.
- **Cons**: The research cost is paid and then thrown away; the next effort re-derives the same conclusions; the reasoning for exclusion is lost, so exclusions read as oversights.
- **Why rejected**: Recording an exclusion with its rationale costs a paragraph and preserves a decision.

## Consequences

### Positive

- No task in this workflow can be blocked by backend work, so the whole effort can be executed and verified end to end.
- The backend integration tests serve as the authoritative specification of every behavior the UI must accommodate, removing ambiguity about error cases and business rules.
- The delivery is verifiable on completion, because the pipeline gate is repaired as part of it.

### Negative

- The product ships without a bulk data path for residents, so onboarding an existing condominium means entering residents one at a time.
- No export means administrators needing a report will continue to work outside the product.

### Risks

- **Risk**: The frontend may surface a gap where the API cannot express something a screen needs. **Mitigation**: The API contract was mapped in full before writing this PRD, including filterable fields, sortable columns, and the exact error envelope; the known gaps are recorded as Open Questions rather than discovered mid-build.
- **Risk**: Excluding import may be read downstream as "import is unimportant". **Mitigation**: Non-Goals carries the market evidence and the reason, explicitly framed as deferred rather than rejected.

## Implementation Notes

The API's response envelope, pagination metadata, filter-parsing rules and error-code mapping are uniform across all four modules because they derive from one shared CRUD router. A single client-side data-access pattern therefore serves all four screens.

Business-rule violations arrive as HTTP 409 without per-field detail, whereas schema violations arrive as 422 with a field path. The UI must treat these two classes differently: the former as a general message, the latter as inline field errors.
