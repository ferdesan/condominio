# ADR-001: Close the unauthenticated file path before pinning the visibility matrix

## Status

Accepted

## Date

2026-09-15

## Context

`document.service.ts:98-119` implements a five-level visibility matrix (`PUBLIC`, `RESIDENTS`, `OWNERS`, `STAFF`, `ADMIN`) and denies a download with 403 when the caller's role is not allowed. This workflow set out to pin that matrix down with an exhaustive integration table (ADR-003).

Exploration found the matrix is bypassable in two requests, through three independent facts:

1. `app.ts:81-88` mounts `express.static` at `/uploads`, rooted at the upload directory. The mount sits **outside** `env.API_PREFIX`, and `authenticate` is installed inside `apiRouter` (`routes/index.ts:41`). The static path therefore has no token check, no tenant scoping and no visibility check.
2. `document.entity.ts:42` declares `filePath` as an ordinary column with no `select: false`, so the stored path is returned in every document response.
3. `assertVisibility` is called only from `prepareDownload` (`document.service.ts:70`). `list` and `findById` are inherited from `BaseCrudService` and never call it.

A `RESIDENT` holds `document:read`. They list `/api/v1/documents`, read `filePath` from an `ADMIN`-visibility record, and fetch `GET /uploads/<filePath>` with no credentials at all.

Stored names are UUIDs (`upload.middleware.ts:38`), so the directory is not blindly enumerable. The API itself hands out the path.

## Decision

Close the bypass first, as `task_01`, and only then write the matrix tests.

1. Remove the `/uploads` static mount from `app.ts`. The sole legitimate read path becomes `GET /documents/:id/download`, which already applies `assertVisibility`, already resolves the path through the traversal guard in `resolveStoredPath`, and already counts the download.
2. Stop returning `filePath`: mark the column `select: false` so the storage layout — which embeds the tenant id — never reaches a client. `document.service.ts` reads the column internally through the repository, which must request it explicitly where needed.
3. Prove both with integration cases: the file is unreachable without credentials, and the authenticated download still works.

Ordering is the point of this ADR. A green matrix over an open side door describes a protection the system does not have.

## Alternatives Considered

### Alternative 1: Authenticate the static mount

- **Description**: Keep `/uploads` and put `authenticate` plus a visibility resolver in front of it.
- **Pros**: Preserves a direct-file URL, which is cheaper for large files than streaming through the service.
- **Cons**: Requires mapping a filesystem path back to a document row to know its visibility — the inverse of the lookup the application is built around. Two code paths would then enforce the same rule, and the duplicate drifts.
- **Why rejected**: `GET /documents/:id/download` already does all of it. A second door that must be taught the same rules is the defect, not the fix.

### Alternative 2: Characterize the bypass with a test and leave it open

- **Description**: Add a case asserting the file is served without authentication, record it as known behavior, ship the matrix tests as planned.
- **Pros**: Keeps this workflow purely additive; no production change.
- **Cons**: Turns an authorization defect into a green assertion. The eleven matrix cases would claim a guarantee the deployed system does not offer.
- **Why rejected**: Rejected by the product owner when the finding was raised, on the grounds that the matrix is the reason the documents spec exists.

### Alternative 3: Also apply `assertVisibility` to `list` and `findById`

- **Description**: Extend the matrix beyond download, so a resident cannot even see that an `ADMIN` document exists.
- **Pros**: Makes visibility mean one thing everywhere.
- **Cons**: Changes list results for every existing caller, and the current split may be deliberate — "you may know it exists, you may not read it" is a coherent product rule.
- **Why rejected**: Out of scope and not a defect on its face. Recorded as an open question in the TechSpec instead.

## Consequences

### Positive

- The visibility matrix becomes the only way a stored file is read, so the tests in ADR-003 measure a real guarantee.
- Storage layout, including tenant ids, stops leaving the server.

### Negative

- `filePath` disappears from the document payload. The frontend declares it in `types/document.ts:51` and in a test fixture but never reads it, so the removal is type-level only — still, it is a breaking change to a published response shape.

### Risks

- An undiscovered consumer outside this repository may fetch `/uploads` directly. Mitigation: nothing in `frontend/src` builds such a URL, and no other service exists in the compose file. The risk is limited to clients not in version control.

## Implementation Notes

Remove the mount rather than guarding it, so no future change can re-open it by relaxing a middleware. `express.static` also serves with `maxAge: '1h'`, meaning any file fetched before this change may sit in an intermediate cache; this closes the path, it does not recall what already left.
