# ADR-007: Block Management Embedded in the Units Screen

## Status

Accepted

## Date

2026-09-12

## Context

Creating a unit requires a block identifier, and the field is mandatory — the schema accepts no unit without one. Bulk generation carries the same requirement, since it produces units within a single block.

Blocks have a complete backend module with the standard CRUD surface, and the navigation already reserves an entry for them. That entry, like every other one outside the dashboard, resolves to the placeholder component. No interface exists to create a block.

The consequence is a hard dependency with no path through it: on a newly registered condominium there are no blocks, so no unit can be created individually or in bulk. The units module would ship unusable in precisely the onboarding scenario that ADR-005 exists to serve. None of the four source specifications mentions blocks, so the gap is absent from the written requirements and only surfaces against the API contract.

## Decision

Block management is embedded in the units screen rather than promoted to a separate module. The unit form's block selector allows creating a block inline, and the units screen offers management of the selected condominium's blocks — name, type, floor count, units per floor, and elevator presence.

The dedicated blocks route remains a placeholder and is not activated by this effort.

## Alternatives Considered

### Alternative 1: A fifth module with its own route

- **Description**: Build a full blocks CRUD at the reserved route; units merely consume it.
- **Pros**: Conceptually cleaner separation; activates a navigation entry that is currently dead; blocks become manageable independently of units.
- **Cons**: Expands the effort by roughly a fifth; adds a CRUD none of the source specifications requested; forces the operator to leave units, create a block, and return mid-registration.
- **Why rejected**: The scope cost buys separation the user has not asked for, and it splits one continuous task — registering a building — across two screens.

### Alternative 2: Assume blocks already exist

- **Description**: Units consumes a block selector and the PRD assumes blocks are seeded or created outside the product.
- **Pros**: Smallest possible scope; units stays a pure CRUD.
- **Cons**: Every newly registered condominium blocks immediately; the assumption holds only for seeded demonstration data, not for a real tenant.
- **Why rejected**: It ships a module that cannot be used for its primary purpose, and it undermines ADR-005 entirely.

## Consequences

### Positive

- A building can be taken from empty condominium to fully registered units in one screen and one sitting.
- The mandatory dependency is satisfied without adding a route or a module to the effort.
- The blocks backend module gains an interface without committing to a full module now.

### Negative

- Block management is discoverable only from the units screen, which is not where a user would first look for it.
- The reserved blocks route stays a placeholder, so the navigation entry continues to lead nowhere.

### Risks

- **Risk**: Embedded management may grow into a full CRUD by accretion, quietly becoming the fifth module this decision avoided. **Mitigation**: Scope it to what unit registration requires — create, list, edit and delete a block — and leave anything beyond that to the dedicated module when it is built.
- **Risk**: Deleting a block with units may be refused or may orphan units. **Mitigation**: Surface the server's response; the unit-to-block relationship is enforced server-side and its refusal message is specific.

## Implementation Notes

Block fields are name, type — block, tower, wing or street — floor count, units per floor, and elevator presence. The floor and units-per-floor values are natural defaults for the bulk generation flow, since they describe the same building geometry.

A block belongs to exactly one condominium, and the server refuses a unit whose block belongs to a different condominium. Offering only the selected condominium's blocks prevents the mismatch from arising.
