# ADR-007: The New Permission Reaches Seeded Roles Through a Data Migration

## Status

Accepted

## Date

2026-09-18

## Context

Adding `financial-closing` to `RESOURCES` (`shared/constants/resources.ts:2-34`)
is enough for the catalog, the `Resource` type and the five
`financial-closing:*` permissions to exist, and for `ROLE_DEFINITIONS` to grant
`manage` to ADMIN and SÍNDICO automatically — ADMIN through
`manageAll(...RESOURCES.filter((r) => r !== 'tenant'))` and SÍNDICO through
`OPERATIONAL_RESOURCES` (`shared/constants/roles.ts:26-58`).

Those definitions describe what a role *should* hold. What a role actually holds
is a `simple-json` array persisted when the tenant was seeded
(`role.entity.ts:19-20`), and `RoleService.beforeUpdate` refuses to change the
permissions of a system role (`role.service.ts:37-41`). The seed is idempotent
and returns early for an existing tenant (`seed.ts:79-88`), so it will not
repair those rows either.

The result is a failure the test suite cannot see: tests run against a schema
built by `synchronize: true` and a seed that runs from zero, so every role has
the new permission. A deployed MySQL database has roles that do not, and the new
screen answers 403 to every user in it — including the tenant administrator.

## Decision

The migration that creates `financial_closings` and adds the opening-balance
columns also patches the data: for every role with `is_system = true` whose
`name` is `ADMIN` or `SINDICO`, append `financial-closing:manage` to the
`permissions` JSON array when it is not already there.

`down()` removes the same string from the same rows, so a revert leaves no
permission naming a resource the code no longer knows.

The patch names the two roles literally rather than deriving them from
`ROLE_DEFINITIONS`. A migration is a statement about the database at one point
in time; reading it against constants that keep changing would make it mean
something different next year.

STAFF and RESIDENT are untouched, matching their explicit definitions. RESIDENT
in particular reads no statement here: this is a back-office, and the resident
portal that would consume `financial-closing:read` does not exist in this
frontend.

## Alternatives Considered

### Alternative 1: New tenants only

- **Description**: no data migration; existing tenants reach the statement by
  creating a custom role.
- **Pros**: nothing to write, and no migration touching data.
- **Cons**: every existing installation ships a screen its administrator cannot
  open, and the remedy is a manual procedure nobody is told about.
- **Why rejected**: it moves the cost onto whoever operates the system, to save
  about fifteen lines.

### Alternative 2: Make the seed reconcile system roles on every run

- **Description**: the seed stops returning early and rewrites the permission
  array of all five system roles each time it runs.
- **Pros**: solves this case and every future one.
- **Cons**: changes the meaning of the seed for all five roles at once, and the
  seed runs in environments where an operator may have deliberately diverged.
  The blast radius is every permission of every system role, to deliver one
  string.
- **Why rejected**: disproportionate, and it hides a migration inside a script
  whose job is to create data.

### Alternative 3: Relax `RoleService.beforeUpdate` for this case

- **Description**: allow permission edits on system roles.
- **Pros**: the permission could then be granted through the API.
- **Cons**: removes a guard that exists to keep seeded roles predictable, in
  order to avoid writing a migration.
- **Why rejected**: it trades a protection for a convenience.

## Consequences

### Positive

- A deployed database and the code's own role definitions agree after deploy,
  with no manual step.
- The revert is symmetric, so rolling the feature back leaves no dangling
  permission.

### Negative

- This is the first migration in the repository to touch data rather than
  schema, and the first to `ALTER TABLE` at all — the two existing ones only
  create and drop tables.
- JSON manipulation inside a migration is database-specific. It is written as a
  read-modify-write over the rows in TypeScript rather than as a MySQL JSON
  function, so it stays readable and portable.

### Risks

- A tenant that renamed its ADMIN or SÍNDICO role is not matched and does not
  receive the permission. Accepted: system roles are seeded with fixed names.
- Nothing in the test suite exercises this migration, because tests never run
  migrations (`data-source.ts:17-24`). Mitigation: `_tests.md` pins the
  permission expectations of the seeded roles, which catches the constants half.
  The migration half is verified by running `migration:run` against MySQL, and
  that verification is a task step, not a test case.

## Implementation Notes

The data patch runs after the `CREATE TABLE` inside the same `up()`, so a
partial deployment cannot leave the table present and the permission missing.
