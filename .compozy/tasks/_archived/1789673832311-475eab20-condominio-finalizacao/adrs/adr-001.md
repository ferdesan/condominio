# ADR-001: LGPD Data Deletion Strategy

## Status

Accepted

## Date

2026-09-16

## Context

The LGPD (Art. 18, VI) grants data subjects the right to request deletion of personal data processed based on consent. The condominium SaaS platform collects personal data from residents, dependents, employees, and service providers including names, CPFs, emails, phone numbers, and addresses. Currently, the system implements soft deletes (`deleted_at` column) for operational recovery but has no mechanism for definitive personal data deletion as required by law.

The platform must comply with LGPD Art. 16, which permits retention only for legal compliance, judicial proceedings, or exercise of legal rights — all other personal data must be deleted upon request.

## Decision

Implement real physical deletion of personal data fields when a data subject exercises their LGPD deletion right. The approach:

1. **Anonymize before delete**: Replace all personally identifiable fields (name, CPF, email, phone, address) with anonymized values (e.g., `REDACTED-{hash}`) before physical deletion, preserving referential integrity for financial records that may be legally required.
2. **Preserve financial/legal records**: Charges, payments, expenses, and audit logs that reference the deleted entity retain their transactional data but with the personal fields anonymized. This satisfies LGPD Art. 16 exceptions (legal obligations, tax records).
3. **Cascade to dependents**: When a resident is deleted, all linked dependents are also anonymized/deleted.
4. **Audit trail**: Log the deletion request and execution in the audit trail with action `LGPD_DELETE` for accountability (Art. 37).

## Alternatives Considered

### Alternative 1: Soft delete with flag

- **Description**: Add an `lgpd_deleted` boolean flag and hide data from queries while preserving it in the database
- **Pros**: Simple to implement, reversible, no referential integrity issues
- **Cons**: Does not meet LGPD Art. 16 requirement for actual deletion; data still exists in the database; ANPD could consider this non-compliant
- **Why rejected**: LGPD requires actual deletion or anonymization, not just hiding data

### Alternative 2: Full physical deletion of all records

- **Description**: Delete the resident row and all dependent rows entirely, including financial records
- **Pros**: True compliance with deletion right
- **Cons**: Breaks financial records, tax documentation, and audit trails; may violate other legal obligations (Código Tributário, arts. 326-328)
- **Why rejected**: Conflicts with legal retention requirements for financial/tax data

### Alternative 3: Anonymization-only (no physical delete)

- **Description**: Replace all personal fields with anonymized values but never delete the row
- **Pros**: Preserves all referential integrity, simple to implement
- **Cons**: Row still exists (may confuse administrators), no true "deletion" — could be challenged as insufficient
- **Why rejected**: While anonymization is valid under LGPD, combining it with physical deletion of the row (after anonymization) provides stronger compliance

## Consequences

### Positive

- Full LGPD Art. 18, VI compliance (right to deletion)
- Financial and tax records preserved for legal compliance
- Audit trail of all deletion requests for accountability
- Referential integrity maintained across the system

### Negative

- Anonymized records still occupy database space
- Deletion is irreversible once executed
- More complex than simple soft delete

### Risks

- **Risk**: Financial records lose meaning after anonymization
  - **Mitigation**: Anonymize only personal identifiers, preserve transaction amounts, dates, and categories
- **Risk**: Admin accidentally deletes active resident
  - **Mitigation**: Add confirmation dialog, require active session, check for active charges/reservations before deletion

## Implementation Notes

- Create a new `lgpd_requests` table to track deletion requests and their status
- Add a `POST /lgpd/delete-request` endpoint for residents to request deletion
- Add an `POST /lgpd/delete-request/:id/execute` endpoint for admins to execute deletion
- Anonymization function should replace: `name` → `REDACTED-{uuid}`, `cpf` → `000.000.000-00`, `email` → `redacted@redacted.invalid`, `phone` → `0000000000`, `address` fields → empty
- Run anonymization within a database transaction to ensure atomicity
- Log the operation in `audit_logs` with `action: LGPD_DELETE`
