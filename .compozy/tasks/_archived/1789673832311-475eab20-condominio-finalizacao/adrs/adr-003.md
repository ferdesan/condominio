# ADR-003: Testing Priority Strategy

## Status

Accepted

## Date

2026-09-16

## Context

The platform has significant test coverage gaps across both backend and frontend. The backend has 4 modules without integration tests and 0 of ~30 services with unit tests. The frontend has 74 test files (947 cases) but critical infrastructure providers (`auth-provider`, `theme-provider`), the authorization system (`permissions.ts`, `ProtectedRoute`), and most feature sub-components lack dedicated tests.

Given that testing every untested file would be an enormous effort, a priority-based strategy is needed to maximize risk reduction per unit of effort.

## Decision

Prioritize testing in three tiers based on security sensitivity and risk:

### Tier 1 — Critical Security Infrastructure (highest priority)
- `auth-provider.tsx` — Session lifecycle, login/logout, token management
- `permissions.ts` — Authorization logic used by every route and UI action
- `protected-route.tsx` — Route guard controlling access to all protected pages
- Backend: `dependents`, `employees`, `service-providers`, `residents` integration tests (4 missing modules)

### Tier 2 — High-Value Business Logic
- `theme-provider.tsx` — Theme persistence and system detection
- `query-provider.tsx` — Error handling and retry configuration
- `use-account-theme.ts`, `use-chart-colors.ts` — Non-trivial hooks
- `utils.ts` — Pure utility functions
- Financial module components (13 untested components, highest complexity)

### Tier 3 — Supporting Components
- Feature hooks (`*-hooks.ts`) — Tested indirectly through page tests
- Feature schemas (`*-schema.ts`) — Partially covered by form dialog tests
- UI primitives (`components/ui/`) — Thin wrappers around Radix
- Layout components (`sidebar.tsx`, `topbar.tsx`, `app-shell.tsx`) — Partially covered by router tests

## Alternatives Considered

### Alternative 1: Coverage-first (aim for X% coverage)

- **Description**: Set a coverage target (e.g., 80%) and write tests until reached
- **Pros**: Clear metric, easy to track progress
- **Cons**: May prioritize low-value tests (testing thin wrappers) over high-value security logic; arbitrary number doesn't correlate with risk
- **Why rejected**: Risk-based prioritization provides better protection per unit of effort

### Alternative 2: Module-by-module (complete one module at a time)

- **Description**: Fully test one feature module before moving to the next
- **Pros**: Each module becomes fully covered incrementally
- **Cons**: Leaves critical infrastructure (auth, permissions) untested for longer; modules with thin wrappers get disproportionate attention
- **Why rejected**: Infrastructure tests have higher risk-reduction value than completing individual modules

### Alternative 3: TDD for new features only

- **Description**: Only write tests for new code going forward, skip backfilling existing gaps
- **Pros**: Minimal effort, prevents regression in new code
- **Cons**: Critical security infrastructure remains untested indefinitely; existing bugs go undetected
- **Why rejected**: The auth/permissions infrastructure is already built and deployed — testing it is essential for production safety

## Consequences

### Positive

- Critical security paths (auth, authorization) get tested first
- Backend coverage gaps in 4 modules closed early
- Risk-based approach maximizes protection per unit of effort
- Tier 3 items can be tested incrementally without blocking delivery

### Negative

- Full coverage of all components deferred to Tier 3 (may never reach 100%)
- Some indirectly-tested code (hooks, schemas) may remain without dedicated tests

### Risks

- **Risk**: Tier 1 tests may be complex to write (mocking auth providers, JWT tokens)
  - **Mitigation**: Use existing test infrastructure (`renderWithProviders` from `test/render.test.tsx`), mock `localStorage` for tokens
- **Risk**: Backend integration tests require database setup
  - **Mitigation**: Use existing `sql.js` in-memory test setup from `backend/tests/setup.ts`

## Implementation Notes

### Tier 1 Test Plan

**`auth-provider.tsx` tests:**
- Session restore on app boot (valid token in localStorage)
- Login flow (success, failure, account lockout)
- Logout flow (token revocation, local cleanup)
- Token refresh (automatic, expired token handling)
- `updateUser` function
- Session expired event listener

**`permissions.ts` tests:**
- `hasPermission()` with various role/permission combinations
- `hasAnyPermission()` with wildcard matching
- Edge cases: empty permissions, undefined role, `*` wildcard

**`protected-route.tsx` tests:**
- Initializing state (shows loader)
- Unauthenticated user (redirects to /login)
- Authenticated user without required permission (shows ForbiddenPage)
- Authenticated user with required permission (renders children)

**Backend integration tests:**
- `dependents`: CRUD, validation, soft delete, tenant isolation
- `employees`: CRUD, contract types, soft delete, tenant isolation
- `service-providers`: CRUD, soft delete, tenant isolation
- `residents`: CRUD, unit linkage, soft delete with dependents, tenant isolation
