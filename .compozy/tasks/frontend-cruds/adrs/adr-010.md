# ADR-010: The Transport Module as the Test Seam

## Status

Accepted

## Date

2026-09-12

## Context

The frontend has no tests. The harness is otherwise ready: the test runner is configured with a browser-like environment, a setup file, path aliases and global test APIs, and the assertion and interaction libraries are installed and typed. What is missing is any way to supply data to a component under test — no HTTP mock is present.

The pipeline currently fails because the test command finds no test files and exits non-zero, and that job gates the build. So the first test is also the pipeline repair.

The transport module is a natural seam. Its helpers already unwrap the response envelope and normalise every failure into one error type carrying status, code and per-field details, so a test supplying data at that level works with typed domain objects rather than with wire payloads. Its own logic — envelope unwrapping, error normalisation, token refresh, session expiry — is meaningful and testable independently.

The query client is constructed per mount rather than as a module singleton, with a comment stating this exists so tests do not share cache between cases. Isolation is therefore already handled.

## Decision

Component and page tests replace the transport module with a test double, supplying typed fixtures and typed errors directly. The transport module's own behavior is covered by its own unit tests against a mocked HTTP client.

A shared render helper mounts a component inside the query provider, a memory router, and the authentication and condominium contexts, with role and selected condominium supplied per test.

## Alternatives Considered

### Alternative 1: A network-level mock

- **Description**: Add a service-worker-based HTTP mock and define handlers that answer in the API's real wire format.
- **Pros**: Exercises the transport module for real, interceptors included; handlers document the contract, including the distinct error envelopes for validation and business-rule failures; tests survive refactors of the transport layer.
- **Cons**: A new dependency and per-suite server lifecycle; the token-refresh path must be modelled or suppressed in every suite; failures are harder to attribute, since a test can fail inside machinery it did not mean to exercise.
- **Why rejected**: The fidelity it buys is concentrated in the transport module, which is better served by direct unit tests. For screen tests it adds a layer between the test and its intent.

### Alternative 2: Unit tests of pure logic only

- **Description**: Test formatters, parameter assembly and the hook factory; render nothing.
- **Pros**: Fast and stable; no mocking strategy needed at all.
- **Cons**: Leaves all five screens untested, which is what the PRD's pipeline story explicitly rules out — the suite would pass without verifying anything delivered.
- **Why rejected**: It repairs the pipeline without meeting its purpose.

## Consequences

### Positive

- Fixtures are typed domain objects, so a fixture that drifts from the contract fails type checking rather than failing at runtime.
- Error-path tests are direct: constructing the error type with a status and field details exercises the same path the transport module produces.
- Tests are fast, with no server lifecycle and no network.

### Negative

- The transport module's real behavior is absent from screen tests, so a defect in envelope unwrapping would pass them. Its own unit tests are the compensating control, and they must cover it properly.
- A change to the transport module's signatures breaks every test double at once. This is visible and mechanical rather than subtle.

### Risks

- **Risk**: Test doubles may drift from the real signatures over time. **Mitigation**: The double is typed against the real module's exported types, so drift fails type checking.
- **Risk**: The browser-like test environment lacks APIs the interactive components require — notably the layout observer used by charts and the scroll and pointer-capture methods used by the select primitive. Without them, a test that opens a select fails for reasons unrelated to the code under test. **Mitigation**: Add these to the shared setup file as part of this work, rather than per suite.

## Implementation Notes

The setup file currently polyfills only the media-query API. It must also provide the layout observer, the intersection observer, scroll-into-view, and pointer-capture methods before any test renders a select or a dialog.

The test runner's file discovery uses its default pattern and the type checker includes only the source directory, so tests live beside the code they cover.

The coverage provider is not installed, so the coverage command fails on a missing dependency. It is added here, since the pipeline references coverage output.

The test command must also not fail merely because a suite is empty; once tests exist this is moot, but the behavior is what makes the pipeline brittle today.
