# ADR-002: Two thematic spec files, not one per module

## Status

Accepted

## Date

2026-09-15

## Context

Five backend modules have no integration coverage: `documents`, `dependents`, `employees`, `service-providers` and `common-areas`. The first four appear in no line of `backend/tests/integration/`; the fifth appears once, as setup in `reservations.spec.ts:30`.

The eight specs that exist are organised by theme, not by module. `operations.spec.ts` alone covers incidents, correspondences, visitors, vehicles, announcements, maintenances and notifications. `condominium-structure.spec.ts` covers condominiums, blocks, units and residents.

File granularity is not free here. `setupTestContext()` initialises an in-memory SQLite schema and runs the full seed — 32 units, ~30 residents, 96 charges, 3 common areas — and the module registry makes that happen **once per spec file**. Jest runs with `--runInBand`, so the cost is serial.

## Decision

Two new files, following the thematic convention:

- `documents.spec.ts` — upload, the visibility matrix, download, and deletion. Genuinely different from everything else in the suite: the only multipart route, the only one that touches the filesystem, the only one with a role matrix of its own.
- `cadastros.spec.ts` — `dependents`, `employees`, `service-providers` and `common-areas` under four sub-describes. All four are plain `createCrudRouter` modules whose rules are of one kind: a document-format check, a date-ordering check, and a parent-consistency check.

`reservations.spec.ts` is not touched. An earlier draft of this decision put the common-area delete guard there, next to the reservations it depends on; ADR-004 removed that guard from scope, which emptied the extension.

## Alternatives Considered

### Alternative 1: One spec file per module

- **Description**: `documents.spec.ts`, `dependents.spec.ts`, `employees.spec.ts`, `service-providers.spec.ts`, `common-areas.spec.ts`.
- **Pros**: A reader looking for one module's coverage knows exactly which file to open; no sub-describe nesting.
- **Cons**: Five full seeds instead of two. Breaks with the convention of all eight existing specs, leaving the directory organised two different ways at once.
- **Why rejected**: The cost is paid on every run, and the benefit — findability — is already served by sub-describes named after the module.

### Alternative 2: Three files, splitting common-areas out

- **Description**: `documents.spec.ts`, `cadastros.spec.ts`, `common-areas.spec.ts`.
- **Pros**: Keeps the registry file focused on people and companies.
- **Cons**: A third seed for what is, after ADR-004, four assertions about a schema asymmetry.
- **Why rejected**: Not enough content to justify its own seed.

## Consequences

### Positive

- Two seeds instead of five, on a suite that already runs serially.
- The directory keeps one organising principle.

### Negative

- `cadastros.spec.ts` holds four unrelated domains. Its sub-describes must carry the module name so a failure report still says where the problem is.
- State accumulates across `it` blocks within a file — there is no `beforeEach` reset anywhere in this suite. Four domains in one file means four sets of created rows coexisting; each sub-describe must scope its own reads by an identifier it created rather than assuming an empty table.

### Risks

- A single long file grows until nobody reads it whole. Mitigation: if a fifth domain is ever added to `cadastros.spec.ts`, split by then-obvious theme instead of appending.

## Implementation Notes

Both files follow the skeleton every existing spec uses: module-level `let ctx`, personas resolved in `beforeAll` through `login(ctx, seedUsers.<persona>)`, and `afterAll(teardownTestContext)` passed by reference. `documents.spec.ts` is the exception — it needs a combined `afterAll` that removes the tenant's upload directory before tearing the context down.
