# ADR-005: Bulk Unit Generation as the Onboarding Path

## Status

Accepted

## Date

2026-09-12

## Context

Market research identified data migration as the sector's dominant complaint: published grievances against condominium management vendors concentrate on inadequate system implementation rather than missing features. Competitors answer this with spreadsheet import, one of them with assisted column mapping. ADR-001 places import outside this effort because it requires backend surface that does not exist.

One mass-creation path does exist. The units module exposes a generation endpoint taking a condominium, a block, a floor count, a units-per-floor count, a starting floor, a numbering pattern and shared defaults for type, monthly fee and area. It creates the resulting grid, skipping numbers that already exist, and returns how many it created. If every generated number already exists it fails with a business-rule violation rather than reporting zero.

Without it, registering a 120-unit building means 120 dialog submissions.

## Decision

The units screen includes a generation flow exposing this endpoint: the operator supplies the block, the floor range, the units per floor, the numbering pattern and the shared defaults, and receives a count of units created.

## Alternatives Considered

### Alternative 1: Individual registration only

- **Description**: Units is a plain CRUD; buildings are entered unit by unit.
- **Pros**: Smaller scope; uniform with the other three modules; one less flow to design and test.
- **Cons**: Leaves a built endpoint without an interface; makes onboarding an existing building impractical, which is the documented conversion blocker.
- **Why rejected**: With import already excluded, removing generation too would leave the product with no viable path to populate a building.

## Consequences

### Positive

- A building becomes registrable in one operation, which is what onboarding requires.
- It partially offsets the absence of import without any backend work.

### Negative

- Generation produces uniform units. Buildings with varied layouts per floor will need individual editing afterwards.
- It does not help with residents, who remain one at a time.

### Risks

- **Risk**: An operator may generate a large grid against the wrong block and create many unwanted records. **Mitigation**: The flow states the exact count and numbering that will be produced before submission; existing numbers are skipped, so re-running against a populated block is not destructive.
- **Risk**: A run where every number already exists fails rather than reporting zero created, which reads as an error rather than a no-op. **Mitigation**: Surface the returned message, which states that all numbers already exist.

## Implementation Notes

The numbering pattern defaults to a floor-and-index composition where the index is zero-padded to two digits. Floors accept 1 to 100, units per floor 1 to 50. The generation succeeds partially by design: numbers already present in the block are skipped silently, and the response reports only the count created.

Units carry a status that the residents module overwrites automatically — a unit with at least one active resident becomes occupied, otherwise vacant, except where its status is renovation or blocked. Generated units therefore start vacant and change as residents are attached, which the interface should not present as directly editable without noting the interaction.
