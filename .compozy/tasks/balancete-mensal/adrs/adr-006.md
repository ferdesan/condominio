# ADR-006: Export by Browser Print and Client-Side CSV

## Status

Accepted

## Date

2026-09-18

## Context

A statement exists to be distributed: read in an assembly, filed by the
accountant. The plan deliberately left the format open and asked for it to be
confirmed before building, noting that server-side PDF adds a dependency and
that browser printing with a stylesheet might be enough
(`docs/balancete-mensal-plano.md`, "Fatia 4").

The payload the screen already holds is the entire document — there is nothing
the server could add to a rendering that the client does not have.

## Decision

Two exports, neither of which adds a dependency or a route.

1. **Print.** A `@media print` stylesheet turns the statement section into the
   document: the shell, the navigation, the section switcher, the filters and
   every button disappear; the month, the condominium name, the provenance line
   of the opening balance and the closed/open state remain. The síndico prints
   or saves as PDF through the browser.

2. **CSV.** A button builds the file in the browser from the payload already
   loaded and hands it over through a `Blob` and an object URL — the anchor
   mechanics `downloadDocument` already establishes
   (`document-hooks.ts:197-219`), minus the request. Semicolon-separated and
   CRLF-terminated, with a UTF-8 BOM, because the consumer is Excel in pt-BR;
   decimal comma for the same reason.

The CSV carries the same lines as the screen, in the same order, including
"Sem categoria" and the reconciliation line of ADR-004.

## Alternatives Considered

### Alternative 1: PDF generated on the server

- **Description**: a route returning a PDF, downloaded as `/documents` does.
- **Pros**: byte-identical output for everyone, archivable, independent of the
  browser doing the printing.
- **Cons**: a new runtime dependency (`pdfkit`, or headless Chromium, which is
  far heavier than this product), and the layout maintained twice — once in
  React, once in the generator — with nothing keeping them equal.
- **Why rejected**: the cost is a permanent maintenance obligation, and the
  browser already prints.

### Alternative 2: CSV only

- **Description**: the accountant is served, the assembly is not.
- **Pros**: trivial.
- **Cons**: nobody reads a statement to an assembly from a spreadsheet.
- **Why rejected**: it drops the primary audience.

### Alternative 3: Defer the whole slice

- **Description**: ship the first three slices and decide later.
- **Pros**: the decision would be made against a real screen.
- **Cons**: a statement that cannot leave the screen is not yet a statement.
- **Why rejected**: the product owner chose to include it, and the chosen form
  is cheap enough not to warrant staging.

## Consequences

### Positive

- No dependency, no route, no permission: whoever can read the statement can
  export it.
- The printed document cannot disagree with the screen, because it **is** the
  screen.

### Negative

- Output varies with browser and printer settings — margins, page breaks, and
  whether the reader lets the browser print background colors. The stylesheet
  can only ask.
- A closed month printed from the screen carries no archival guarantee. It is a
  printout, not a filed document.

### Risks

- `jsdom` does not implement `URL.createObjectURL` or link download, and does
  not compute layout, so no test proves the printed page looks right. Mitigation
  (already the practice in this repository): stub the two, spy on
  `HTMLAnchorElement.prototype.click`, and test the CSV as a pure function over
  the payload — the part that can be wrong in a way that matters.

## Implementation Notes

The CSV builder is a pure function in the feature's own module, next to the
labels, and not inside the component file: a function exported beside a
component adds an `only-export-components` warning, and this repository holds
its lint warning count at five.
