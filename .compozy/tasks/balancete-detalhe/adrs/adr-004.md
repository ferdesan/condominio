# ADR-004: The Whole Month in One Response, Paged on the Client

## Status

Accepted

## Date

2026-09-18

## Context

The movements of a month are a list the screen has to show, print and export.
The repository has one established way to show a long list — `useListState` plus
`DataTable` with server pagination, as Auditoria (`audit-page.tsx:44-196`) and
Notificações do — and `DataTable` supports both modes: by default it renders
whatever `data` it is given and takes `currentPage` / `totalPages` /
`onPageChange` from outside, and `clientPagination` opts into slicing a
collection already in memory (`data-table.tsx:165-168`).

Server pagination and the document pull in opposite directions. `MAX_PER_PAGE`
is 200 (`query-params.ts:14`), so a five-hundred-unit month does not fit in a
page, and both exports would need a second, complete fetch that the screen never
displays — two code paths reading the same month, one of which nobody looks at
until the output is wrong.

## Decision

`GET /financial/closings/:referenceMonth/entries` returns **every movement of the
month in one response**, unpaginated. The table pages on the client with
`clientPagination`.

Printing and CSV read the payload the screen already holds, which is what
`balancete-mensal` ADR-006 established for the summary and what keeps the
exported document identical to the displayed one by construction.

The response is `{ entries: StatementEntry[] }` — an object rather than a bare
array, so a later addition (a count, a truncation flag) does not change the shape
of what is already published.

## Alternatives Considered

### Alternative 1: Server pagination, as Auditoria does

- **Description**: `useListState` + `DataTable` with `currentPage`/`totalPages`.
- **Pros**: constant payload; sorting and filtering by the database; the pattern
  two screens already follow.
- **Cons**: the exports need a separate full read, so the file and the screen are
  produced by different paths; and the 200-row ceiling means the full read is
  itself several requests.
- **Why rejected**: the document has to leave the screen complete, and the
  cheapest way to guarantee that is for the screen to hold it complete.

### Alternative 2: Whole month, with a ceiling and a notice

- **Description**: return everything up to a limit, and tell the reader when the
  list was cut, offering the CSV as the complete path.
- **Pros**: bounded payload; the large condominium degrades visibly instead of
  silently.
- **Cons**: the CSV would then be built from something the screen does not have,
  reintroducing the second path this decision exists to avoid.
- **Why rejected**: not chosen, but it is the first thing to reach for if the
  payload ever becomes a problem — recorded here so the next person does not
  have to rediscover it.

## Consequences

### Positive

- One read, one payload, one document: screen, print and CSV cannot disagree.
- No pagination state to keep in sync with a month selector.
- `clientPagination` exists for exactly this and has not been used anywhere yet.

### Negative

- The payload grows with the condominium. Five hundred movements is on the order
  of 60 KB of JSON — fine over a LAN, noticeable on a phone.
- Sorting and filtering happen in the browser, so they operate on what was sent
  and cannot reach beyond it. That is correct here: what was sent *is* the month.

### Risks

- A condominium far larger than this product's current shape would make the
  response slow before it makes it wrong. The ceiling of Alternative 2 is the
  prepared answer.

## Implementation Notes

The endpoint does not accept `page` or `perPage`. Accepting and ignoring them
would invite a caller to believe a page was applied.
