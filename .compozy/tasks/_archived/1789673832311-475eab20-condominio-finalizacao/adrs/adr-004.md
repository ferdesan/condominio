# ADR-004: LGPD Module Structure

## Status

Accepted

## Date

2026-09-16

## Context

The LGPD compliance feature requires multiple capabilities: data deletion requests, data export, and consent management. The existing codebase follows a strict 1-module = 1-entity pattern (e.g., `residents/`, `vehicles/`, `documents/`). However, LGPD has three distinct sub-domains that need to coexist under a cohesive API surface.

## Decision

Implement LGPD as a **single module** (`lgpd/`) with a unified router at `/lgpd` and three sub-route groups:

- `POST /lgpd/delete-request` — Create deletion request
- `GET /lgpd/delete-requests` — List deletion requests (admin)
- `POST /lgpd/delete-request/:id/execute` — Execute deletion
- `POST /lgpd/delete-request/:id/cancel` — Cancel deletion
- `GET /lgpd/export` — Export personal data
- `GET /lgpd/consent` — View consent status
- `POST /lgpd/consent` — Update consent

The module will have:
- **One entity file** (`lgpd.entity.ts`) defining `LgpdRequest` and `LgpdConsent` entities (two tables, one module)
- **One repository file** per entity (`lgpd-request.repository.ts`, `lgpd-consent.repository.ts`)
- **One service file** (`lgpd.service.ts`) orchestrating all three capabilities
- **One schema file** (`lgpd.schema.ts`) with Zod schemas for all request types
- **One routes file** (`lgpd.routes.ts`) with custom routes (not using `createCrudRouter` since the endpoints are non-standard)

## Alternatives Considered

### Alternative 1: Three separate modules

- **Description**: `lgpd-requests/`, `lgpd-exports/`, `lgpd-consents/` as independent modules
- **Pros**: Follows the existing 1:1 pattern exactly; each module is self-contained
- **Cons**: Three routers, three services, three sets of routes for a closely related feature; makes the API surface fragmented; harder to coordinate deletion + consent in a single transaction
- **Why rejected**: LGPD operations are logically coupled (a deletion request checks consent status; consent revocation triggers warnings); splitting them adds coordination overhead without benefit

### Alternative 2: Extend existing Resident entity

- **Description**: Add LGPD fields directly to the Resident entity and routes
- **Pros**: No new tables; LGPD is a property of the resident
- **Cons**: Mixes compliance logic with domain logic; the Resident entity becomes bloated; export and deletion request tracking need their own storage; violates single-responsibility
- **Why rejected**: LGPD has its own lifecycle (requests, audit, status tracking) that doesn't fit as simple columns on Resident

## Consequences

### Positive

- Cohesive API surface under `/lgpd` prefix
- Single service coordinates cross-cutting concerns (consent check before deletion)
- Follows the project's module convention (entity + repository + service + schema + routes)
- Easy to add new LGPD capabilities later (e.g., data portability to external systems)

### Negative

- Two entities in one module breaks the strict 1:1 pattern (minor deviation)
- Custom routes instead of `createCrudRouter` (LGPD operations are not standard CRUD)

### Risks

- **Risk**: Two entities in one module may confuse future developers
  - **Mitigation**: Clear file naming (`lgpd-request.entity.ts`, `lgpd-consent.entity.ts`) and JSDoc comments

## Implementation Notes

- `LgpdRequest` entity tracks deletion requests with status lifecycle
- `LgpdConsent` entity tracks consent grants/revocations with timestamps
- The `lgpd.service.ts` will import `residentRepository` and `dependentRepository` for the anonymization cascade
- The export endpoint will query multiple repositories (residents, dependents, vehicles, etc.) but will not create a new entity — it generates JSON on-the-fly
