# ADR-003: The Freeze Covers Only Writes That Move Cash

## Status

Accepted

## Date

2026-09-18

## Context

A statement that changes after it is published is not an account rendered. The
plan asked for an act of closing and, after it, for new entries in that month to
be refused (`docs/balancete-mensal-plano.md`, "3. O que significa 'fechado'?").

The plan's wording — "a new entry with competence/payment in that month is
refused" — predates the choice of cash basis. Under ADR-001 a charge's
`reference_month` contributes nothing to the statement: creating, editing or
deleting a charge referencing a closed month cannot change a single number in
it. Refusing it would be a rule that protects nothing, and rules that protect
nothing teach people to reopen months for no reason.

What can move a closed month is narrow and enumerable:

- a payment whose `paid_at` falls in the month (`ChargeService.registerPayment`);
- an expense entering, leaving, or changing its paid state or amount with
  `paid_at` in the month (`create`, `update`, `pay`, `remove`, `restore`).

Two shapes in the existing code complicate where the check goes:

- `registerPayment` writes the charge through `this.repository.update`, not
  through `BaseCrudService.update` (`charge.service.ts:223-231`), so
  `beforeUpdate` never runs for a payment.
- `BaseCrudService` has no `beforeRestore` hook (`base-crud.service.ts:89-97`),
  so restoring a soft-deleted paid expense into a closed month cannot be caught
  by a hook.

## Decision

Closing a month refuses exactly the writes that move cash in it.

The check is a guard function, not a service dependency:
`assertMonthOpen(scope, condominiumId, when)` in
`backend/src/modules/financial/closing-guard.ts`, depending only on the closing
repository — the shape `shared/services/reference-guard.ts` already establishes.
It throws `BusinessRuleError` (409) naming the month and the way out
("reabra o mês para lançar").

Call sites, all of them:

| Where | Trigger |
|---|---|
| `ChargeService.registerPayment` | `dto.paidAt`, inline before the payment row is created |
| `ExpenseService.prepareCreate` | `dto.paidAt` when the expense is born `PAID` |
| `ExpenseService.prepareUpdate` | the current `paid_at` and the new one, when either changes or the amount does |
| `ExpenseService.pay` | `dto.paidAt` |
| `ExpenseService.beforeRemove` | the current `paid_at` of a `PAID` expense |
| `ExpenseService.restore` (overridden) | the current `paid_at` of a `PAID` expense |

Charges are untouched: generating, editing, cancelling charges and applying late
fees all remain legal against a closed month, because none of them reaches the
statement.

The way out of a refusal is `POST /financial/closings/:referenceMonth/reopen`,
which is recorded on the closing row (`reopened_at`, `reopened_by_id`,
`reopen_count`) and audited, and which requires `financial-closing:manage` —
a stronger permission than closing itself.

## Alternatives Considered

### Alternative 1: Refuse charges by competence as well

- **Description**: a closed month refuses charge writes referencing it.
- **Pros**: one sentence to explain — "a closed month is closed"; no reader has
  to know which fields feed the statement.
- **Cons**: blocks work that cannot change the document, in a system where
  billing a past month is a legitimate correction.
- **Why rejected**: the product owner chose to freeze what moves the number. The
  auxiliary delinquency figure, the one charge-derived number the document
  shows, is frozen by storing it (ADR-005) rather than by blocking writes.

### Alternative 2: Refuse everything, including bulk generation and late fees

- **Description**: no write reaches a closed month by any path.
- **Pros**: maximally rigid, trivially explainable.
- **Cons**: `applyLateFees` operates across months by design; forbidding it
  against any closed month would make it unusable as soon as one month is
  closed.
- **Why rejected**: it would break a working feature to protect a number that
  feature does not touch.

### Alternative 3: Put the check in `BaseCrudService` hooks only

- **Description**: rely on `beforeUpdate` / `beforeRemove`.
- **Pros**: no inline calls; one place.
- **Cons**: misses `registerPayment` entirely (it bypasses the hooks) and
  `restore` (no hook exists) — the two paths that most need it.
- **Why rejected**: it would look complete and leave the main door open.

## Consequences

### Positive

- Every refusal corresponds to a number that would otherwise have changed, so
  the rule can be explained by pointing at the statement.
- The guard is a function over a repository, so no service imports another
  service and no import cycle is created.

### Negative

- Six call sites instead of one hook. A seventh write path added later to
  expenses or payments will not inherit the guard, and nothing forces the author
  to remember. Mitigation: the guard lives in the financial module next to what
  it protects, and `_tests.md` pins each site.
- `ExpenseService.restore` has to be overridden purely to add a check, which is
  the first override of `restore` in the codebase.

### Risks

- `ExpenseService.pay` schedules the next occurrence of a recurring expense
  (`expense.service.ts:74`). That insert lands in a **later** month, which is
  open, so it is not refused — but it means paying one expense creates another.
  The statement is unaffected; the behavior is noted so nobody reads it as a
  leak in the freeze.

## Implementation Notes

`assertMonthOpen` takes the instant, not the month string, and derives
`YYYY-MM` itself, so no call site formats a date.
