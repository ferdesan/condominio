# ADR-003: Pin the visibility matrix exhaustively, table-driven

## Status

Accepted

## Date

2026-09-15

## Context

`assertVisibility` (`document.service.ts:98-119`) decides who may download a document. It has two layers:

- anyone holding `document:manage` passes unconditionally — that is `admin`, `sindico` and `superAdmin` in the seed;
- everyone else is judged by `roleName` against the document's visibility: `PUBLIC` and `RESIDENTS` allow all, `OWNERS` allows all but `STAFF`, `STAFF` allows only `STAFF`, `ADMIN` allows nobody.

Only two seeded personas lack `document:manage`: `porteiro` (`STAFF`) and `morador` (`RESIDENT`). The decision space that the rule actually discriminates is therefore 5 visibilities × 2 personas = 10 outcomes, of which 4 are denials, plus one case for the manage shortcut.

The rule keys off `roleName`, not off resident type. A `TENANT` resident downloads an `OWNERS` document, because the check never looks at `Resident.type`.

## Decision

Cover all ten combinations in one `it.each` table, plus one case proving the `document:manage` shortcut, for eleven cases total.

The table is written with the expected status inline, so the matrix is readable as a matrix:

```ts
it.each([
  ['PUBLIC',    'porteiro', 200], ['PUBLIC',    'morador', 200],
  ['RESIDENTS', 'porteiro', 200], ['RESIDENTS', 'morador', 200],
  ['OWNERS',    'porteiro', 403], ['OWNERS',    'morador', 200],
  ['STAFF',     'porteiro', 200], ['STAFF',     'morador', 403],
  ['ADMIN',     'porteiro', 403], ['ADMIN',     'morador', 403],
])('%s baixado por %s responde %i', ...)
```

Each row uploads a document at that visibility in `beforeAll` — one upload per visibility, reused by both personas — and asserts the status of the download.

## Alternatives Considered

### Alternative 1: Boundaries only — the four denials plus two controls

- **Description**: Assert the four 403s, one permitted download and the manage shortcut. Six cases.
- **Pros**: Shorter; covers everything that protects information.
- **Cons**: The untested half is the half that *grants* access. A regression that widens `OWNERS` to include `STAFF` produces no failure, and widening is the direction that leaks.
- **Why rejected**: The cases omitted are exactly the ones a permissive regression would trip.

### Alternative 2: One persona per visibility — five cases

- **Description**: Touch each visibility once, choosing the persona that best demonstrates it.
- **Pros**: The minimum that names all five levels.
- **Cons**: `OWNERS` and `STAFF` are defined by the asymmetry between the two personas; one row each asserts half a rule.
- **Why rejected**: For the two levels that matter most, it tests nothing about what makes them distinct.

## Consequences

### Positive

- A new visibility level added to the server breaks the table rather than slipping through — the row count is part of the assertion surface.
- The table doubles as documentation of a rule currently expressed as a `Record` of booleans plus a special case.

### Negative

- Eleven cases for one function is the densest coverage in the backend suite; it will look disproportionate next to `auth.spec.ts`, which has eight cases for the whole authentication module.

### Risks

- The table encodes `roleName` semantics. If roles are ever renamed, ten cases fail at once and the cause will be one constant. Mitigation: rows reference `seedUsers` keys, not raw role strings.

## Implementation Notes

Uploading five documents in `beforeAll` requires five real files on disk. Use in-memory buffers through `.attach('file', Buffer.from(...), { filename, contentType })` — no fixture directory exists in this repository and none should be added for this.

Note the ordering interaction with ADR-001: these cases are only meaningful once `/uploads` no longer serves the same bytes without credentials.
