# ADR-008: Resource-Hook Factory as the Data-Access Layer

## Status

Accepted

## Date

2026-09-12

## Context

All four modules plus blocks are served by one shared CRUD router on the backend, so their HTTP surface is byte-identical in shape: the same success envelope, the same pagination metadata, the same reserved query parameters, the same seven routes, and the same error-code mapping. Only the resource segment of the path and the payload types differ.

The frontend has no data-access layer. The one real page declares its queries inline, which is the established convention. Applied to this effort that convention produces roughly twenty-four near-identical query and mutation declarations across five resources, each repeating the query-key shape, the pagination parameters, the enabled guard on the selected condominium, and the invalidation targets. Five copies of a rule is five places to update when the rule changes, and query-key drift between a mutation's invalidation and a list's key is silent — the list simply fails to refresh.

The modules diverge sharply above that layer. Reservations carry a calendar and an approval workflow, units carry bulk generation and embedded block management, condominiums carry a detail page, residents carry exclusive primary designation. A configuration-driven CRUD component would meet each divergence with an escape hatch.

## Decision

A factory in `frontend/src/lib/crud/` produces the React Query hooks for a resource from its path segment and its types: list, get, create, update, remove, and restore. Each feature instantiates it once in a small module beside its page, and writes its own interface by hand.

The factory owns query-key composition, pagination parameter assembly, filter serialisation, sort-direction translation, and invalidation. It owns no rendering.

## Alternatives Considered

### Alternative 1: Inline queries per page, following the existing convention

- **Description**: Each page declares its own queries and mutations, as the dashboard does.
- **Pros**: Zero indirection; matches the single precedent in the codebase; every page reads top to bottom with nothing hidden.
- **Cons**: Roughly twenty-four repetitions of the same five-line shape; query-key and invalidation drift fails silently; a change to the pagination or filter contract must be applied in five places.
- **Why rejected**: The repetition is mechanical rather than incidental — these calls are identical because the backend deliberately made them identical.

### Alternative 2: A configuration-driven CRUD page component

- **Description**: One component receives resource, columns, filters and form schema, and renders the whole screen.
- **Pros**: Maximum reuse if the screens were uniform; a new resource would cost a configuration object.
- **Cons**: The screens are not uniform — calendar, approval queue, bulk generation, embedded blocks and a detail page each require an escape hatch, and a component driven by six render props is harder to follow than five explicit pages.
- **Why rejected**: It abstracts the layer that differs while leaving untouched the layer that repeats.

## Consequences

### Positive

- One definition of the query-key convention, so a mutation's invalidation cannot drift from the list it must refresh.
- Pagination, filtering and sorting are translated to the API's contract in one place, including the sort-direction case difference the table component and the API disagree on.
- Each screen stays explicit and readable, so divergent features need no escape hatch.

### Negative

- Introduces an abstraction with no precedent in this codebase, so it must be documented where the next contributor will find it.
- A generic factory is harder to type than concrete hooks, and its type parameters will carry the complexity that the call sites shed.

### Risks

- **Risk**: The factory accretes resource-specific behavior and becomes the configuration-driven component this decision rejected. **Mitigation**: It exposes only the six operations the shared CRUD router provides. Resource-specific endpoints — bulk generation, availability, approve, reject, cancel, statistics — are written as ordinary hooks beside the feature that uses them.
- **Risk**: Generic types may degrade to `any` under pressure, which lint flags as a warning rather than an error. **Mitigation**: Type parameters for the entity, the create payload and the update payload are explicit at each instantiation.

## Implementation Notes

Query keys follow the existing hierarchical convention: `[resource, 'list', params]` for a listing, `[resource, 'detail', id]` for a single record. Mutations invalidate `[resource]`, which covers both.

Condominium mutations additionally invalidate the key the application shell uses for its selector, since both read the same collection.

Reserved query parameters are page, perPage, sortBy, sortOrder, search and includeDeleted; every other key is a filter. Array filter values serialise to a comma-separated string, which the backend parses as a set membership test. Filters not on the resource's server-side whitelist are ignored silently, so only whitelisted filters may be offered.
