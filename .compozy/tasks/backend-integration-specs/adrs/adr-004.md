# ADR-004: Where a test workflow is allowed to change production code

## Status

Accepted

## Date

2026-09-15

## Context

This workflow exists to add missing integration coverage. Exploration surfaced four defects or oddities in the five modules, and each posed the same question: does a workflow chartered to write tests get to change the code it is testing?

1. **`/uploads` serves stored files with no authentication** — the visibility matrix is bypassable (ADR-001).
2. **A failed multipart upload leaks a file.** `document.routes.ts` runs `upload.single('file')` at line 40 and parses the body at line 45. A body that fails validation returns 422 with the file already written to disk, and nothing removes it.
3. **`updateCommonAreaSchema` bypasses both refinements** that `createCommonAreaSchema` applies. `PATCH` accepts `closesAt` earlier than `opensAt`, and `maxHours` below `minHours`; `POST` rejects both with 422.
4. **The common-area delete guard is hand-written SQL** (`common-area.service.ts:19-28`) with snake_case column names, while tests run on SQLite and production on MySQL.

## Decision

Change production code only where the defect has **no observable API surface** — where no test, however well written, could assert the correct behavior against the code as it stands.

**In scope:**

- (1) the `/uploads` bypass. A test can observe it, but asserting it would certify a hole. See ADR-001.
- (2) the orphan file. The route already returns the correct 422; the defect is entirely on the filesystem, invisible to any API assertion. The fix wraps the parse so a failure unlinks `req.file.path` before rethrowing, and a case then asserts the file is gone.

**Out of scope, covered as-is:**

- (3) the `PATCH` asymmetry. Both behaviors are observable and both get cases: `POST` rejects with 422, `PATCH` accepts the same value. The test states what the system does. If the asymmetry is a defect, the test is where that argument starts, with a number attached.

**Out of scope, not covered:**

- (4) the delete guard. Excluded on the product owner's call. A test would run against SQLite and could not speak for the MySQL behavior that matters; rewriting the query to earn a meaningful test is a production change of the kind this ADR declines.

## Alternatives Considered

### Alternative 1: Purely additive — no production change at all

- **Description**: Write tests only; record all four findings as follow-ups.
- **Pros**: The smallest possible blast radius; the workflow does exactly what its name says.
- **Cons**: Items 1 and 2 would produce tests that assert defective behavior as though it were the contract.
- **Why rejected**: A test that certifies a hole is worse than no test, because it converts an open question into a settled one.

### Alternative 2: Fix everything found

- **Description**: Close all four, then test all four.
- **Pros**: The modules leave this workflow correct rather than merely described.
- **Cons**: Items 3 and 4 are product decisions, not defects on their face. Tightening `PATCH` would start rejecting requests that succeed today, in a release whose stated purpose was adding tests.
- **Why rejected**: Behavior changes that break existing callers need their own decision, with the owner of the API in the room.

## Consequences

### Positive

- One rule decides every case, and it is checkable: can a test observe the correct behavior without changing the code? If yes, test it; if no, fix it.
- Items 3 and 4 leave a trail — one as a passing test that documents an asymmetry, the other as this paragraph.

### Negative

- The workflow ships production changes in two files, so a failure during rollout could come from the fix rather than from a test. The build order in the TechSpec puts both changes first, alone, for exactly this reason.
- Item 4 stays uncovered, and the delete guard is the only business rule `common-areas` has.

### Risks

- "No observable API surface" is a judgement, and the next finding may sit on the line. Mitigation: when it does, it goes to the product owner as a question, which is how all four of these were settled.

## Implementation Notes

The orphan fix belongs in the route, not in the service: `req.file` exists only there, and the service is never reached when the body fails to parse. Unlink failures must be swallowed — a cleanup error must not replace the 422 the client needs to see.
