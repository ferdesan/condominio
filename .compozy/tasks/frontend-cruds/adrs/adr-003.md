# ADR-003: Monthly Calendar With Filterable List and an Inline Approval Queue

## Status

Accepted

## Date

2026-09-12

## Context

The source specification for reservations asks for monthly, weekly and daily calendar views. The project has no calendar library; the dependency list carries a date utility library and a tab primitive, but nothing that renders a time grid. Weekly and daily views require positioning entries along an hour axis with overlap resolution — substantially more work than the month grid, and plausibly more than any one of the three CRUD screens in this effort.

The backend offers an availability endpoint that accepts a condominium, an optional common area, and a date range, returning a flat array of pending and confirmed reservations ordered by start time, each carrying the area name and unit number. This shape suits a calendar render directly, at any range granularity.

Separately, reservations are the only module in this effort with a review workflow. When a common area requires approval, a reservation is created in a pending state and only a holder of the reservation manage permission may approve or reject it, optionally with a reason. Approval re-validates the slot against conflicts, so it can fail even after the request was accepted. The backend notifies the requester on the outcome.

## Decision

The reservations screen delivers a monthly calendar view backed by the availability endpoint, alongside the standard paginated and filterable list. Weekly and daily views are excluded and recorded as Non-Goals.

Approval and rejection are inline actions on the reservation row, and the screen surfaces the count of pending requests as an entry point that applies the pending filter in one interaction. No separate approvals screen is created.

## Alternatives Considered

### Alternative 1: All three calendar views, as specified

- **Description**: Monthly, weekly and daily views switched by tabs.
- **Pros**: Faithful to the written specification; a daily view is genuinely useful for a heavily-booked area.
- **Cons**: The hour-grid layout is the most expensive component in the effort and would likely dominate its schedule; no library is present, so it is built from scratch; the value over a filtered list is marginal at typical booking volumes.
- **Why rejected**: Cost concentrated in one view, displacing work on three modules that currently have no interface at all.

### Alternative 2: List only, no calendar

- **Description**: Treat reservations as a fourth CRUD with period and status filters.
- **Pros**: Smallest scope; perfect consistency across the four screens.
- **Cons**: Loses the visual read of availability, which is the question the screen exists to answer — whether a given area is free on a given date.
- **Why rejected**: Reduces the module to a table over a domain that is inherently temporal.

### Alternative 3: A separate approvals screen

- **Description**: A dedicated route for the pending queue.
- **Pros**: A focused dispatch surface, uncluttered by the full reservation history.
- **Cons**: Adds a fifth screen; splits reservations across two locations the user must remember; the pending queue is a status filter over the same data.
- **Why rejected**: The list already filters by status, so a separate route duplicates a view that a filter provides.

## Consequences

### Positive

- The calendar answers the availability question without a new dependency, using the date utilities already present.
- Approval stays where the reservation is, so a síndico clearing ten pending requests does so from one list.
- A single availability request populates a whole month.

### Negative

- An area booked in overlapping slots within one day is hard to read on a month grid, since a day cell cannot convey intra-day layout.
- Weekly and daily planning remain outside the product.

### Risks

- **Risk**: Approval may fail on conflict even after the reservation was accepted as pending, which reads as an inconsistency to the user. **Mitigation**: The failure carries a specific message about an existing confirmed reservation for the slot; surfacing it verbatim and refreshing the view explains the outcome.
- **Risk**: A month cell with many reservations overflows. **Mitigation**: Cap visible entries per day with a residual indicator, and rely on the list for exhaustive reading.

## Implementation Notes

The nine slot-validation rules enforced on creation — end after start, no past dates, advance-booking limit, minimum and maximum duration, permitted weekdays, opening-hours window, overlap with pending or confirmed reservations, and minimum interval between bookings by the same unit — all return HTTP 409 with a specific message and no field path. The common-area record carries the parameters behind each of these rules, so the form can surface the constraints before submission, but the server remains the authority.

Reservation states are pending, confirmed, rejected, canceled and completed. Completed and canceled reservations are immutable. Cancellation of an already-started reservation is restricted to administration.
