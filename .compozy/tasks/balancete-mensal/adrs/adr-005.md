# ADR-005: A Closed Month Is a Stored Document, Not a Recomputed View

## Status

Accepted

## Date

2026-09-18

## Context

The statement has to survive being reprinted. A closed month read in September
must give the number it gave in March, and the per-category table under it must
give the same lines — including for a category that was renamed, deactivated or
soft-deleted in between, and for a charge whose category was corrected after the
fact.

Freezing only the three headline totals would leave the table underneath free to
drift away from them, which is the worst of both: totals that agree with the
past and a breakdown that agrees with the present.

The category lines are a document, not queryable domain rows: nothing filters,
sorts or joins them after the fact. The codebase already stores documents of
this shape in `simple-json` columns — `role.permissions`
(`role.entity.ts:19-20`) and `tenant.settings` (`tenant.entity.ts:10-27`).

## Decision

One table, `financial_closings`, holding the whole document:

| Column | Type | Meaning |
|---|---|---|
| `condominium_id` | `VARCHAR(36)` | scope |
| `reference_month` | `VARCHAR(7)` | `YYYY-MM` |
| `status` | `VARCHAR(20)` | `OPEN` · `CLOSED` |
| `opening_balance` | `DECIMAL(12,2)` | inherited or computed (ADR-002) |
| `total_income` | `DECIMAL(12,2)` | cash in |
| `total_expense` | `DECIMAL(12,2)` | cash out |
| `closing_balance` | `DECIMAL(12,2)` | opening + income − expense |
| `overdue_amount` | `DECIMAL(12,2)` | auxiliary delinquency, frozen |
| `overdue_count` | `INT` | auxiliary delinquency, frozen |
| `breakdown` | `simple-json` | the category lines and the reconciliation line |
| `closed_at` / `closed_by_id` | `DATETIME(6)` / `VARCHAR(36)` | who and when |
| `reopened_at` / `reopened_by_id` / `reopen_count` | `DATETIME(6)` / `VARCHAR(36)` / `INT` | the record of reopening (ADR-003) |

Unique on `(tenant_id, condominium_id, reference_month)`.

**A row exists only once a month has been closed.** No row means the month was
never closed, which is the same thing as open; `status = 'OPEN'` means it was
closed and then reopened. Reading treats both as open, and closing again
overwrites the same row rather than creating a second one.

`GET /financial/closings/:referenceMonth` therefore has two modes: it recomputes
while the month is open, and it serves `breakdown` plus the stored totals once
the month is closed. The response shape is identical either way — the caller
learns which mode it got from `status` and `closedAt`, not from a different
payload.

Category names are resolved `withDeleted` at close time and written into
`breakdown`, so a category deleted afterwards keeps its name in the document. A
null `category_id` becomes an explicit "Sem categoria" line, never a dropped
value.

## Alternatives Considered

### Alternative 1: Store totals only; recompute the breakdown

- **Description**: three numbers frozen, the table always live.
- **Pros**: one fewer column; no serialized shape to version.
- **Cons**: the table can stop summing to the frozen total — a category renamed,
  a charge recategorized, a soft-deleted category losing its name.
- **Why rejected**: the document has to be internally consistent, and the
  breakdown is most of what a reader actually reads.

### Alternative 2: A child table of closing lines

- **Description**: `financial_closing_lines` with one row per category.
- **Pros**: relational; queryable across months without parsing JSON.
- **Cons**: a table, a repository, a join and a cascade, for rows nothing ever
  queries individually.
- **Why rejected**: no reader of these lines is a query. If cross-month
  analytics ever arrives, it can be built by projecting the JSON.

### Alternative 3: Recompute everything, always; `closed` is only a flag

- **Description**: nothing stored but the status.
- **Pros**: no snapshot to keep honest; one code path.
- **Cons**: reprinting March in September can give a different number, which is
  the exact failure the closing exists to prevent — and the freeze of ADR-003
  does not cover the auxiliary delinquency figure, which is charge-derived and
  legitimately mutable.
- **Why rejected**: it is the problem, not a solution to it.

## Consequences

### Positive

- Reading a closed month touches one row and no aggregate at all.
- The frozen delinquency figure lets ADR-003 leave charge writes unrestricted
  without the document drifting.
- Re-closing is idempotent by construction: the unique index makes a second
  close an update of the same row, not a duplicate.

### Negative

- `breakdown` is a serialized shape with no schema enforcement in the database.
  A change to its fields has to tolerate rows written by the previous shape.
- Two read paths through one endpoint. They must return the same shape, and
  nothing but a test forces them to.

### Risks

- The stored document can be made stale by a direct SQL write, which no guard
  can reach. Accepted: this is a back-office over a database its operators own.

## Implementation Notes

The recompute path and the stored path are built to produce one another: the
close operation persists exactly the object the recompute path returned, and the
read of a closed month returns exactly what was persisted. The test contract
pins that equality rather than the two shapes separately.
