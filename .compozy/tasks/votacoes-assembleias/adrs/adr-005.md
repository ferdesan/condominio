# ADR-005: Dedicated vote-status summary endpoint

## Status

Accepted

## Date

2026-09-22

## Context

The management dialog (ADR-003) needs one row per unit of the poll's condominium with status Already voted / Pending / Not eligible, without revealing the chosen option. `GET /polls/:id/votes` returns 403 whenever `isSecret` is true (`poll.service.ts` `listVotes`), so it cannot feed the status list on secret polls — and even on open polls it returns full `Vote` rows (option, voter identity) that the dialog must not display. A read model that is safe for secret ballots and carries eligibility is missing.

## Decision

Add `GET /polls/:id/vote-status` guarded by `authorize('vote:manage')`. The service loads units of the poll's condominium, the poll's votes (internal read — not via `listVotes`), and active OWNER residents when `voterType === 'OWNERS'`, then returns `[{ unitId, unitNumber, status }]` with `status ∈ { VOTED, PENDING, NOT_ELIGIBLE }`. No option, no voter identity, no `registeredByUserId`. Works for secret and open polls alike; works for any poll status (read-only).

## Alternatives Considered

### Alternative 1: Redact `GET /votes` for `vote:manage`

- **Description**: Allow managers past the secret 403 and strip option/voter fields from the response.
- **Pros**: No new route.
- **Cons**: Overloads an existing contract (raw `Vote[]` vs redacted rows); every consumer must branch on secret; still does not compute eligibility or units that never voted.
- **Why rejected**: Wrong shape for the dialog; eligibility and "never voted" units require a different join anyway.

### Alternative 2: Client-side join of units × votes

- **Description**: Frontend fetches units and `GET /votes`, merges locally.
- **Pros**: No backend change.
- **Cons**: `GET /votes` is 403 on secret polls — the primary case fails; ships full vote rows to the client only to discard fields.
- **Why rejected**: Cannot satisfy ADR-003 on secret ballots.

## Consequences

### Positive

- Secret-safe status list with a single request; eligibility computed where the rules already live.
- Dialog never receives option or identity fields, so the UI cannot leak them by accident.

### Negative

- One more route and service method to maintain; status is a snapshot (client refetches after proxy submit).

### Risks

- Hundreds of units in one response — acceptable (small objects, no relations); filter client-side. Revisit only if a condominium exceeds ~1k units.

## Implementation Notes

Register inside `pollRouter` `extend` next to the other `/:id/*` literals. Batch-load OWNER residents by condominium (`type=OWNER`, `status=ACTIVE`) once, not per unit. Proxy submit (`POST /:id/votes`) must use the same eligibility rule (ADR-007).
