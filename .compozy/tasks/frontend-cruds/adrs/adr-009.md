# ADR-009: Repairing the Shared Table Component In Place

## Status

Accepted

## Date

2026-09-12

## Context

The shared table component was delivered as a completed task and documented, but it has never been consumed — the dashboard does not use it, and no other screen exists. Reading it against the API contract surfaces four defects that all five listings in this effort would hit immediately:

1. It truncates its input with a slice to the page size on every render, unconditionally. With server-side pagination the server already returns exactly one page, so the slice is a no-op only while the component's page size matches the request's page size. Any mismatch silently drops rows.
2. Its search input is uncontrolled and fires the callback on every keystroke, with no debounce and no way to clear it programmatically.
3. It reports sort direction in lower case while the API expects upper case, so a direction passed through unchanged is not the direction requested — the API falls back to descending without error.
4. Its column key is typed as a key of the row type, so an actions column has no valid key. The component's own documentation suggests a key the type system rejects.

Additionally its clickable rows carry no keyboard affordance, which fails the accessibility bar the PRD sets.

The component has zero consumers, so changing it cannot regress anything.

## Decision

The defects are fixed in the component itself. The slice becomes conditional on client-side pagination being requested. The search input accepts a controlled value and leaves debouncing to its caller, which owns the request. Sort direction is translated at the data layer rather than in the component, so the component keeps its own vocabulary. The column key accepts a string identifier alongside a row key, so an actions column is expressible. Clickable rows gain keyboard activation and the semantics that go with it.

Its documentation is updated in the same change.

## Alternatives Considered

### Alternative 1: Wrap it in an adapter

- **Description**: A wrapper compensates for each defect from outside — matching page sizes, translating direction, debouncing before delegating.
- **Pros**: The delivered component stays byte-identical; the task that produced it remains untouched.
- **Cons**: The defects stay alive in a shared component for the next consumer to rediscover; the wrapper exists solely to work around code the same team owns; two components must be understood to read one table.
- **Why rejected**: Preserving a component's bytes is not the same as preserving its value, and with no consumers there is nothing to protect.

### Alternative 2: Replace it

- **Description**: Write a table designed for server-side pagination and retire the existing one.
- **Pros**: A cleaner result, unconstrained by existing choices.
- **Cons**: Discards delivered and documented work whose structure — column definitions, empty and loading states, pagination controls — is already right; leaves two table components until someone removes the old one.
- **Why rejected**: The component's shape is sound. Four localised defects do not justify replacing it.

## Consequences

### Positive

- All five listings inherit correct behavior rather than each compensating for the same four defects.
- The accessibility bar the PRD sets is met by the shared component instead of per screen.
- The next consumer of the table finds it correct.

### Negative

- A component documented as complete changes, so its documentation must change with it or become misleading.
- Anyone who read the component before this change carries a stale mental model.

### Risks

- **Risk**: Widening the column key type weakens type safety for ordinary columns. **Mitigation**: The key remains a row key where the column renders a field; only columns supplying their own renderer may use a free identifier.
- **Risk**: Changes to a shared component may be scoped loosely and drift into a rewrite. **Mitigation**: The change is bounded to the four defects and the keyboard affordance; anything else is out of scope.

## Implementation Notes

The page size and the requested page size must agree when server-side pagination is used. The data layer owns the request and the component owns the display, so the page size flows from the data layer into the component rather than being set independently in each screen.

Debouncing belongs to the caller because the caller issues the request. The component accepting a controlled value is what makes that possible.

The component defaults search, sort and pagination to enabled, and hides its pagination controls entirely when the total page count is one — which is also the default. A screen that does not supply the total page count therefore loses its pagination silently.
