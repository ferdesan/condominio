# ADR-004: A Paid Expense Must Carry Its Payment Date

## Status

Accepted

## Date

2026-09-18

## Context

Under ADR-001 the expense side of the statement is `SUM(expense.amount)` over
rows with `status = 'PAID'` and `paid_at` inside the month. A row that is `PAID`
with `paid_at` null therefore belongs to no month: the money left the account
and the statement never shows it, in any month, with no error and no warning.

That row is creatable today through the ordinary API. `createExpenseSchema`
accepts `status: z.enum(EXPENSE_STATUSES).default('PENDING')` and
`paidAt: z.coerce.date().optional().nullable()`
(`schemas/financial.schema.ts:87,96`), and neither `prepareCreate` nor
`prepareUpdate` checks that the two agree (`expense.service.ts:31-53`). The
update schema is the partial of the create schema, so setting `status: 'PAID'`
alone is a valid request.

Only `ExpenseService.pay` sets both together, and the seed does it correctly
(`seed.ts:550-597`) — which is why no existing test notices.

This workflow is a feature workflow, not a bugfix workflow. The precedent for
changing production code from inside one is `backend-integration-specs`
ADR-004: change it when the feature being built would otherwise certify a
guarantee the system does not offer.

## Decision

Two changes, in the same task.

1. **The invariant.** `ExpenseService.prepareCreate` and `prepareUpdate` refuse
   a state where `status = 'PAID'` and `paid_at` is null, with
   `BusinessRuleError` (409) — "Uma despesa paga precisa da data de pagamento."
   The check reads the *resulting* state, not the payload, so an update that
   sets `PAID` on a row that already has `paid_at` passes, and an update that
   clears `paid_at` on a row that is already `PAID` fails.

2. **The reconciliation line.** The statement carries, outside the balance, a
   line "Pagas sem data de pagamento" for expenses with `status = 'PAID'`,
   `paid_at IS NULL` and `competence` equal to the month, with count and total.
   It is attributed by competence because that is the only month such a row
   claims, and it is kept out of every total because the statement is cash.

The line is part of the stored snapshot (ADR-005), so a month closed while such
rows existed keeps saying so.

## Alternatives Considered

### Alternative 1: Add the invariant and nothing else

- **Description**: close the hole; assume no row is in that state today.
- **Pros**: smallest change; no line to explain on screen.
- **Cons**: if a row does exist in a deployed database, its value silently
  leaves the statement and the balance is wrong by exactly that amount, with
  nothing to point at.
- **Why rejected**: a total that fails to close because of an omitted line is
  worse than an ugly line. The product owner chose to see the rows.

### Alternative 2: Fall back to `due_date` when `paid_at` is null

- **Description**: treat the due date as the cash date for paid rows missing it.
- **Pros**: nothing is refused, nothing disappears, no new line.
- **Cons**: the month's cash figure would depend on a date that is not a payment
  date, and the error would be invisible — the number would simply be wrong in a
  plausible way.
- **Why rejected**: inventing a cash date defeats the reason the cash basis was
  chosen.

### Alternative 3: Backfill `paid_at` in the migration

- **Description**: set `paid_at = due_date` for offending rows at deploy time.
- **Pros**: the data becomes consistent once and the line is never needed.
- **Cons**: writes a payment date nobody chose into a financial record, in a
  migration, unreviewably.
- **Why rejected**: same objection as Alternative 2, made permanent.

## Consequences

### Positive

- After this task the failure mode cannot be created again, and the existing
  rows are visible instead of absent.
- `ExpenseService.pay` already satisfies the invariant, so the normal path is
  unaffected.

### Negative

- A client that today creates a paid expense in one request without a date
  starts receiving 409. No such client exists in this repository — the frontend
  form always goes through `pay` — but an external integration would break.
- The reconciliation query is a third read per statement.

### Risks

- The invariant is enforced in the service, not in the database, so a direct SQL
  insert can still produce the state. Mitigated, not solved, by the
  reconciliation line, which exists precisely to surface rows the service did
  not create.

## Implementation Notes

The refusal is a `BusinessRuleError`, and `409` is the status this codebase
already uses for a violated business rule (`errors/app-error.ts:58-69`), not
`422`, which belongs to schema validation.
