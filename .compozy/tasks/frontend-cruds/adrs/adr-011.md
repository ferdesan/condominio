# ADR-011: Reservation Validation Split Between Client and Server

## Status

Accepted

## Date

2026-09-12

## Context

Creating a reservation passes nine slot rules on the server, each refusing with its own message and none carrying a field path, so all nine arrive as general messages rather than field errors. Seven are decidable from data the form already holds once a common area is chosen, because the area record carries the parameters for each: the end must follow the start, the start must not be in the past, the start must fall within the advance-booking limit, the duration must meet the minimum and not exceed the maximum, the weekday must be permitted, and the time range must fall inside the opening hours. Capacity is an eighth of the same kind.

Two are not decidable in the client. Overlap with an existing pending or confirmed booking, and the minimum interval since the same unit's last booking of that area, both depend on reservations the client has not read and cannot read atomically with the submission.

Submitting blind means the user discovers nine constraints by trial and error. Replicating all nine means duplicating business rules that will diverge the first time the backend changes, and the two stateful ones would be validated against a stale read that the server must re-check anyway.

## Decision

The form surfaces the chosen area's constraints as guidance, and validates locally the eight rules decidable from the area record and the form's own values. The two stateful rules remain the server's alone, and their refusals are presented as form-level messages.

The server stays the authority for all ten. Local validation only shortens the feedback loop; it never substitutes for the server's answer, and a locally valid submission that the server refuses is a normal outcome, not an error condition.

## Alternatives Considered

### Alternative 1: No local validation beyond shape

- **Description**: Validate only required fields and formats; let the server decide everything else.
- **Pros**: One source of truth; no divergence possible; the smallest schema.
- **Cons**: Nine constraints discovered one failed submission at a time, each requiring a round trip.
- **Why rejected**: The area record already carries every parameter needed to answer eight of them immediately.

### Alternative 2: Replicate all nine, including a conflict pre-check

- **Description**: Fetch the area's existing reservations and check overlap and interval before submitting.
- **Pros**: The best possible feedback, with conflicts surfaced before submission.
- **Cons**: A local conflict check is always a stale read, so the server must re-check regardless; it adds a request to every form interaction; and it duplicates the rule most likely to change.
- **Why rejected**: It pays for duplication without removing the server check it duplicates.

## Consequences

### Positive

- The user sees an area's constraints before entering a time, rather than discovering them through refusals.
- The two rules that genuinely require server state are the only ones that cost a round trip to discover.
- Local rules derive from the area record at runtime, so an area's parameters changing on the server changes the form's behavior without a code change.

### Negative

- Eight rules exist in two places. Their logic is simple and parameterised, but a change to the rule's *shape* — not its parameters — must be made twice.
- A rule the client believes is satisfied may still be refused by the server, which must read as a normal outcome rather than a contradiction.

### Risks

- **Risk**: Local validation drifts from server behavior after a backend change, and the form rejects what the server would accept. **Mitigation**: Local rules are advisory and derived from the area record's parameters; the backend integration tests remain the authority, and a divergence surfaces as a rejected submission rather than a corrupted one.
- **Risk**: Time-zone handling differs between client and server, making a boundary case valid in one and not the other. **Mitigation**: Opening hours are compared as local wall-clock time, matching how the server interprets them; boundary cases at the exact opening and closing minute are covered in the test contract.

## Implementation Notes

The eight local rules are derived from the common-area record at runtime rather than written as constants, so the schema is constructed once an area is chosen. Before an area is chosen, only required fields and the end-after-start relation can be checked.

Server refusals for slot rules carry no field path and must therefore be shown as form-level messages. Schema violations do carry a field path and are shown against the field. The form must distinguish the two by the presence of field detail, not by status code, since conflicts and business-rule violations share one status.

Approval re-runs the overlap check, so a pending reservation can be refused at approval time even though it was accepted when created. That refusal is surfaced on the approval action, not on the form.
