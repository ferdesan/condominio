# ADR-002: Frozen Movements in a Child Table, Not in the Document JSON

## Status

Accepted

## Date

2026-09-18

## Context

`balancete-mensal` ADR-005 made the closed month a stored document: totals in
columns, category lines in a `simple-json` column named `breakdown`. It
explicitly rejected a child table for those lines:

> No reader of these lines is a query. If cross-month analytics ever arrives, it
> can be built by projecting the JSON.

That reasoning holds for category lines and does not survive the movements.

**Volume.** A month has as many income movements as it had payments — one per
unit that paid, plus partials. Thirty-two units in the seed; five hundred in a
real building. `breakdown` is a `TEXT` column, and `TEXT` in MySQL holds **65,535
bytes**. Five hundred movement rows serialise to something on the order of 60–100
KB. The document would fit in the small condominium and truncate in the large
one, which is the worst way for a limit to exist: it works until it silently
does not, and the failure lands on the customer with the most to lose.

**Use.** The category lines are read as a block and never individually. The
movements are the opposite: sorted by date or value, filtered by category,
counted, and paged through. Every one of those is a query.

**Consistency.** The movements cannot be recomputed for a closed month.
`balancete-mensal` IT-276 proves that a write made directly to the database after
closing does not move the frozen totals — so a recomputed list would show a row
the total does not include, and the document would contradict itself on its own
screen. Whatever the screen lists for a closed month has to be as frozen as the
number above it.

## Decision

A child table, `financial_closing_entries`, written when the month is closed.

One row per movement, carrying what the document shows and nothing that depends
on another table still being intact:

| Column | Why it is stored rather than joined |
|---|---|
| `kind` (`INCOME` · `EXPENSE`) | which side of the statement |
| `occurred_at` | the cash date — `payment.paid_at` or `expense.paid_at` |
| `category_id` + `category_name` | the name is denormalized for the same reason the category lines denormalize it: a category renamed or removed later must not rewrite a rendered account |
| `description` | the charge's or the expense's description, as it read that day |
| `counterpart` | the unit number for income, the service provider for expense — the other party, resolved once |
| `amount`, `method` | the money and how it moved |
| `source_id` | the `payment` or `expense` row it came from, **as a reference and not as a link** |

`source_id` is stored because a future question ("which payment was this?") is
cheap to answer if the id is there and impossible if it is not. Nothing in this
workflow navigates to it: a document that links to a row someone may have deleted
would offer a dead end inside a rendered account.

An open month produces the same shape, computed live. The stored rows are read
only when the month is `CLOSED` — which is the same rule `statement` already
follows, and which keeps a reopened month from serving movements that describe a
state it has left.

## Alternatives Considered

### Alternative 1: Extend `breakdown` with the movements

- **Description**: one more key in the JSON already being written.
- **Pros**: no table, no migration for a table, no repository; `readBreakdown`
  already tolerates missing keys, so old closings degrade gracefully.
- **Cons**: the 64 KB ceiling, reached only by large condominiums; and every
  filter or sort becomes an in-memory pass over a parsed blob.
- **Why rejected**: the ceiling. `MEDIUMTEXT` would lift it and leave the second
  objection untouched.

### Alternative 2: Recompute the movements on every read

- **Description**: no storage; the list is a query, closed month or not.
- **Pros**: nothing to write, nothing to migrate, works retroactively for the
  closings that already exist.
- **Cons**: the list can disagree with the frozen totals, which is the exact
  failure the closing exists to prevent.
- **Why rejected**: the product owner chose the frozen list. A document whose
  body contradicts its own summary is worse than a document without a body.

### Alternative 3: Recompute, and show the divergence when it appears

- **Description**: recompute, compare the sum against the frozen total, and say
  so when they differ.
- **Pros**: cheap, retroactive, and turns the contradiction into a tamper
  indicator.
- **Cons**: makes every reader responsible for interpreting a warning that will
  almost always be absent, and leaves the normal case one query heavier.
- **Why rejected**: also not chosen, but it is the best fallback if the storage
  cost ever proves wrong — it is recorded here for that reason.

## Consequences

### Positive

- The list and the totals are the same document and cannot drift.
- Filtering and sorting are the database's job, on indexed columns.
- The category name survives the category, as it already does for the lines.

### Negative

- Closing writes hundreds of rows where it wrote one. See [ADR-003](adr-003.md)
  for how that is made atomic and how a re-close replaces them.
- The closing already stored in the database has no movements. A closed month
  without entries must say so rather than render an empty table that looks like a
  month without movement.

### Risks

- `payments` and `expenses` have **no index on `paid_at`** — `payment.repository.ts`
  indexes `(tenant_id, charge_id)` and `expense.entity.ts` indexes status and
  competence. Every existing aggregation already scans by date without one; a
  screen that lists row by row does it more often. The migration adds the two
  indexes, which pays for the new read and for the aggregations that predate it.

## Implementation Notes

The `counterpart` for income is reached through `payment.charge_id → charge.unit_id
→ unit.number`, joined manually against `Charge` rather than through the relation
— the reason is written at `payment.repository.ts:25-33`: a relation join inherits
the soft-delete filter, and a removed charge would take with it the identity of a
payment that really happened.
