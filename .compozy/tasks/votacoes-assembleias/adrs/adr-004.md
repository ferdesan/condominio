# ADR-004: After voting, show confirmation then results

## Status

Accepted

## Date

2026-09-22

## Context

Market expectation: residents want clear confirmation that their vote counted, and managers want participation visible during an open poll. After `POST /vote` the user currently has no UI. Product decision needed for the post-submit state on `/votacoes/:pollId`.

## Decision

After a successful vote the VotePage transitions to a **confirmation state** ("Voto registrado") and then presents the **poll results** (same data as the existing results panel: participation, quorum, per-option bars), when the user can read results (`poll:read` / results endpoint allows it). If results are not readable, confirmation alone remains. The dialog entry point navigates to the same route so behavior is identical.

## Alternatives Considered

### Alternative 1: Confirmation only

- **Description**: Toast/page says registered; close.
- **Pros**: Minimal; avoids early result disclosure.
- **Cons**: Users must hunt for apuração elsewhere; weaker feedback loop.
- **Why rejected**: User selected confirmation + results.

### Alternative 2: Close immediately to listing

- **Description**: No dedicated feedback.
- **Pros**: Fastest.
- **Cons**: Ambiguity whether the vote stuck; poor accessibility for remote voters.
- **Why rejected**: Too little feedback for a high-stakes action.

## Consequences

### Positive

- Clear completion state; participation pressure via visible quorum (when results readable).

### Negative

- Secret polls: results still aggregate-only (already true server-side); confirmation must not reveal choice on shared screens beyond "you voted".

### Risks

- Showing results before close may influence late voters on open polls — accepted for this product (results endpoint already exists for managers and is not gated to CLOSED-only today).

## Implementation Notes

Reuse `PollResultsPanel` / `usePollResults` on the vote page after success; wire `useMyVote` to prefill "already voted" state on deep link.
