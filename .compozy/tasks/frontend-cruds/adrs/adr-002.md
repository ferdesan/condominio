# ADR-002: Back-Office Personas Only for the Initial Release

## Status

Accepted

## Date

2026-09-12

## Context

The backend's role definitions grant the RESIDENT role create, read, update and delete on reservations, scoped by an ownership check that restricts a resident to their own unit. A resident attempting to reserve for another unit receives HTTP 403. The system therefore already supports resident self-service for reservations.

Supporting that flow in the UI would require more than reusing the administrative screen. The authenticated-user payload returned by the session endpoint includes the resident's unit, but the frontend's user type does not expose it, so the unit would have to be threaded through the session layer. The reservation form would need to hide the unit selector and pre-bind the unit, the ownership rejection would need distinct handling, and the list would need a "my reservations" projection. Cancellation rules also diverge: a requester may cancel their own reservation, but once it has started only administration may cancel it.

The four source specifications are written from an administrative standpoint throughout — they describe listing columns, registration forms and management actions, never a resident-facing journey.

## Decision

The four screens serve back-office personas only: ADMIN, SINDICO, and STAFF in its read-mostly capacity. The síndico creates reservations on behalf of residents, and approves or rejects pending requests.

Resident self-service is recorded as a Non-Goal with the supporting backend capability documented, so a later effort can build it without re-investigating the permission model.

## Alternatives Considered

### Alternative 1: Both audiences in one release

- **Description**: Ship the administrative screens plus a resident-facing reservation flow.
- **Pros**: Exercises backend capability that already exists; self-service removes the síndico as a bottleneck for routine bookings; closer to what competing products offer residents.
- **Cons**: Reservations would carry two distinct interfaces over one data model, roughly 40% more work in that module alone; requires extending the session payload; introduces a second permission-shaped rendering path in every reservation view.
- **Why rejected**: It expands the single most complex module in the effort while the other three have no resident-facing dimension at all, producing an unbalanced release.

### Alternative 2: Resident-first

- **Description**: Build the resident reservation experience first and defer administration.
- **Pros**: Directly serves the largest user population.
- **Cons**: Residents cannot be given a reservation flow before an administrator can register condominiums, units and residents; the data would not exist.
- **Why rejected**: Inverts a hard dependency — the administrative cadastre is a precondition for any resident-facing feature.

## Consequences

### Positive

- All four modules share one interaction model, so patterns established in the first module transfer directly to the rest.
- The permission surface per screen stays small: a role either manages a resource or reads it.
- The session-user contract needs no change.

### Negative

- Residents cannot book common areas themselves; every reservation passes through the síndico, which is a manual step competing products have automated.

### Risks

- **Risk**: Building the administrative reservation form without the resident case in mind may produce a component that resists reuse later. **Mitigation**: The unit selector is the only element that differs; treating unit as a normal form field with a supplied default keeps both paths open.

## Implementation Notes

Role capability across the four resources, as defined by the backend:

- ADMIN and SINDICO: full management of all four resources, including reservation approval and rejection.
- STAFF: read access to all four, plus reservation update — enough to cancel a reservation, not enough to approve or reject one.
- SUPER_ADMIN: unrestricted.

Approval and rejection require the manage action on reservations, which STAFF does not hold. Any interface element offering those actions must be gated accordingly, and the corresponding routes will reject a STAFF request with 403 regardless.
